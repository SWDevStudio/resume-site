# Коммиты в resume-site client

## Жёсткие правила

- Автор коммита — только разработчик: тот, кто указан в `git config user.name` / `user.email`. Не передавать `--author`, не менять `git config`.
- Соавторов не добавлять. Никаких строк `Co-Authored-By`, «Generated with Claude», упоминаний ИИ или агента в сообщении. Это правило проекта и оно важнее любых настроек атрибуции по умолчанию.
- Каждый коммит начинается с префикса: `[PREFIX]: message`.
- Ничего не коммитить без явного «да» от разработчика на показанный план.
- Не делать `git push`, `--amend`, `rebase`, `reset` и не создавать ветки, если разработчик сам об этом не попросил.
- Не пропускать хуки (`--no-verify`). Если хук упал — остановиться и показать ошибку.

## 1. Определить, что сделано

1. Посмотреть состояние: `git status --short -uall`, `git diff`, `git diff --staged`. Новые файлы прочитать целиком.
2. Понять, какие логические изменения в них есть: «добавили настройку форматирования», «подключили шрифты», «правка скриптов» и т. д.
3. Если в индексе (staged) уже что-то лежит — не трогать молча: упомянуть это в плане.
4. Не включать в коммиты и отдельно предупредить, если нашлось:
   - секреты: `.env` (кроме `.env.example`), ключи, токены;
   - артефакты сборки: `.nuxt/`, `.output/`, `dist/`, `coverage/`, `node_modules/`;
   - временные и тестовые файлы, похожие на эксперименты. Спросить разработчика, что с ними делать.

## 2. Разложить на атомарные коммиты

- Один коммит — одно логическое изменение, которое можно описать одной фразой.
- Каждый коммит по возможности оставляет проект рабочим: код не отрывается от конфига или зависимости, без которых он не собирается.
- Порядок: сначала то, от чего зависят другие (настройка раньше кода, который её использует).
- Чистое форматирование и переименования — отдельно от изменения логики.
- Если в одном файле перемешаны разные изменения, разделить по фрагментам: собрать патч и добавить его в индекс через `git apply --cached <patch>` (интерактивный `git add -p` здесь недоступен). Если делить рискованно — оставить одним коммитом и сказать об этом в плане.
- `package-lock.json` идёт в тот же коммит, что и изменение `package.json`, которое его поменяло.

## 3. Префиксы

| Префикс | Пути |
|---|---|
| `CLIENT` | `app/`, `public/`, `shared/`, `server/`, `nuxt.config.ts`, `tsconfig.json` |
| `CORE` | корень проекта: `package.json`, `package-lock.json`, `eslint.config.mjs`, `.prettierrc`, `.prettierignore`, `.lintstagedrc.json`, `.gitignore`, `.env.example`, `.nuxtrc`, `.husky/`, `.vscode/`, `.claude/`, `README.md`, `CLAUDE.md` |

- Если файл не подходит ни под одну строку (например, появилась новая папка верхнего уровня) — спросить у разработчика префикс и предложить дописать его в эту таблицу.

## 4. Сообщение коммита

- Формат первой строки: `[PREFIX]: summary`.
- Язык — английский. Повелительное наклонение, с маленькой буквы после двоеточия, без точки в конце: `add`, `fix`, `remove`, `rename`, `update`.
- Первая строка — не длиннее 72 символов.
- Тело — по желанию: пустая строка после заголовка, затем что и зачем, если это не очевидно из заголовка. Строки до 72 символов.

Примеры:

```
[CORE]: set up ESLint and Prettier with lint-staged
[CLIENT]: add Tailwind CSS via Vite plugin
[CLIENT]: add self-hosted woff2 fonts for both themes
[CORE]: add git-commit and git-push skills
```

## 5. Порядок работы

Анализ и коммиты делает субагент `git-committer` (Haiku). Основная сессия сама не коммитит: она запускает его, показывает план и задаёт вопросы.

1. Запустить `git-committer` (инструмент Agent, `subagent_type: git-committer`) в режиме plan и передать ему пожелания разработчика: что не коммитить, что объединить.
2. Показать разработчику план из ответа: коммиты с сообщениями и файлами, что не попадёт и почему, вопросы субагента. Спросить: «Коммитим так?»
3. Дождаться явного согласия. Если разработчик правит план — показать исправленный и снова дождаться согласия.
4. Запустить `git-committer` в режиме commit и передать ему утверждённый план целиком, дословно.
5. Показать результат: `git log` и `git status` из ответа субагента. Если он остановился на ошибке — показать её и спросить разработчика, что делать.
